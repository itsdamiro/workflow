# SOP: close a slice with `/handoff`

For any assistant. Run it when the slice's work is done; it commits that work and pushes it (ADR 005, amendment of 2026-10-08), so running it is the owner's go-ahead for those two things and no others. There are two closes (ADR 005, amendment of 2026-10-09): `/handoff` is the light close, and `/handoff full` adds the two reviews of the diff and the fresh-reader check of the handoff. `check` is accepted and means `full`. You need the project's repo, the vault path and the owner.

The test for every step is whether it asks for the owner's attention. Do the work quietly; the report names what needs them, and always what changed in the vault.

## Steps

1. **Check the ground, then commit.** `scripts/gates` passes; if it fails, stop and ask the owner how to proceed, and commit nothing. In `full`, run the two reviews first ("The checks" below) and fix their findings; the gates pass again. Then commit the slice's work, because the sync reads committed state: read the diff first (on a public repository, stop on anything private), stage named files only that belong to the slice, and write a message that says why. If you cannot tell whether a changed file belongs to the slice, leave it out and ask. A clean tree (`git status -sb`, apart from local-only files) needs no commit. The rest of `docs/CLOSING_A_SLICE.md` steps 1 to 8 is still the slice's own checklist.
2. **Run the close script.** `python3 scripts/close_slice.py <project-path> <vault-path> --context-tokens <N>` (ADR 005, amendment of 2026-10-09). It runs the vault sync, the stats line and the lint, in that order, and prints one short block that ends with the `vault:` lines, the notes it created and updated, by path. Leave `--context-tokens` out if your adapter cannot tell you the session's context size (the stats row then shows a dash). Under Claude Code, `N` is the output of `python3 adapters/claude/context-report/last_context.py`, run from the workflow checkout; if it exits 1, leave the option out (ADR 015). Exit 0: the push may go ahead. Exit 1: the lint has an error; do not push, list every error and do not fix a note the script did not generate without asking. Exit 2: a script could not run; say so and stop. A refusal or a hint in the block is for the owner to settle, never to force; it does not stop the close. The scripts behind it write only vault notes marked `generated: true` (ADRs 009, 010 and 014).
3. **Scan the slice's diff for patterns.** Read the diff from the last handoff to now (`git diff <ref>..HEAD`), not the whole codebase. For each reusable pattern, draft a note in `Patterns/` with `status: draft`, citing the file and lines it comes from and any ADR. "No new pattern" is a valid result; do not invent one. The drafts wait: they are not an item for the owner to act on, but the report names each one among the vault changes (step 6).

   **3b. Propose notes for the owner's side of the vault (ADR 017).** Nothing here is written until the owner says yes in plain words. Gather two things: the owner's typed messages since the last `/handoff` in this session (all of them if there was none), which under Claude Code are the output of `python3 adapters/claude/capture/owner_messages.py` saved to a temporary file, and the gaps step 2's block reported (a concept with no note, an unlisted topic, a hub that does not link the stats note, a folder with no definition, a `hint: Tags.md does not list type/...` line). Propose only a passage that has no other home (a record, `docs/reference/GOTCHAS.md`, the handoff, an existing note) and that a later session would lose; a passage with a home goes there instead, and "nothing to propose" is a valid result. Ask the owner once, with every proposal shown in full: a capture (the quote, title, notes to link, topics), a new note (its path and whole text), an appended line (the file, the heading if any, and the line) or a value for a closed list in `Tags.md` (the namespace and the word; ADR 017, amendment of 2026-10-09). Propose the value first when a capture waits on it. Where you have a choice prompt, use it (Claude Code: `AskUserQuestion`): one question per proposal, at most four to a prompt and more in further prompts, the exact text and place in the question's preview, the options **Write it** and **Skip**; wording the owner types in the "Other" box means they want it changed first, so show the changed text and ask again. Where you have none (Gemini CLI), show the proposals in the chat and ask for a yes or no to each in plain words. Write each approved one with `python3 scripts/vault_write.py <vault-path> capture|new|add-line|add-value ...` (its usage is at the top of the script; `--source` is the temporary file). Only **Write it**, or a plain yes, writes a proposal; any other answer or none writes nothing, and the proposal is not made again in this slice. A refusal from the script is for the owner to settle, never to force.
4. **Draft the handoff.** Rewrite `docs/HANDOFF.md` (under 60 lines, volatile facts only). Move anything durable to `docs/reference/` or an ADR. Facts come from `git log`, `git status` and the gates, not from memory. In `full`, run the fresh-reader check on it ("The checks" below) until every answer is right.
5. **Push.** Only if the close script exited 0: push the current branch to its upstream, never forced. The git-safety hook may ask the owner to confirm; that is expected. If it exited 1, do not push and say so in the report.
6. **Report to the owner**, short, in this order: what was committed and whether it was pushed; what failed or was refused (the lint errors, a refusal, a gate); **what changed in the vault**; what needs their acceptance, if anything, and nothing that is only waiting; and whether it is safe to start a fresh session. Code and checks that ran cleanly get no narration, but the vault always does (ADR 005, amendment of 2026-10-09, "every report lists the vault notes"): copy the close script's `vault:` lines (notes created, notes updated, by path), then add what you wrote yourself after the script, the pattern drafts of step 3, the captures, new notes and appended lines of step 3b (by path, and for an appended line the line itself), and any other note you created or edited, each by name and marked created or edited. If nothing changed, say "vault: no note changed". The pattern drafts and the notes of step 3b are listed here as changes and never as something waiting. In a plain close, if the diff changed a script, a hook, an adapter or a decision record's Decision section, add one line: "reviews not run: `/handoff full` runs them". In `full`, say what the two reviews and the fresh-reader check found and what was done about each; if one could not run, say which and why, and the close is then not complete.

## The checks (`full` only)

Only in `/handoff full`: read `docs/sop/handoff-full.md` before step 1. It holds the two reviews, the fresh-reader check and the rule that a check is never skipped. A plain close does not read it.

## Under Gemini CLI

Only under Gemini CLI: read `docs/sop/handoff-gemini.md`; the Gemini command loads it with this file. It lists what differs from the steps above.

## Do not

- Commit or push anything but the slice's work: no `git add .`, `-A` or `-u`, no force-push, no attribution trailer, and no commit or push of `docs/HANDOFF.md`, which is local-only. Outside this procedure, commit and push only on the owner's word.
- Skip a check in `full`, or run one without saying so ("The checks" above).
- Edit a note without `generated: true` except to add drafts the owner will review, and what the owner approved in step 3b, written by `scripts/vault_write.py` and nothing more (ADR 017).
- Write anything from this procedure into the project's repository except `docs/HANDOFF.md` and `docs/reference/`.
- List a pattern draft, or anything else that is only waiting, as something the owner must do. Leave a note you wrote out of the report's vault list.
- Put the report's vault list anywhere but the chat: not in a commit message, not in `docs/HANDOFF.md`, not in any file of the project's repository. Vault note names are private and this repository may be public.
